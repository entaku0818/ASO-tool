## Feature 1: 成果シェアLP

### 概要
`/share/{id}` または `/s/{hash}` 形式の未認証アクセス可能ページ。  
URLパラメータ（keyword / current_rank / previous_rank / improvement）から成果カードを表示。  
OGP meta タグにより X(Twitter)/Facebook でリッチプレビュー表示。

### リスク先行分析

> **⚠️ Critical Risk — OGP と `'use client'` の競合**  
> Next.js 14 App Router において `'use client'` ページはクライアントレンダリングされるため、OGP crawlerはメタタグを取得できない。  
> LP ページを SSR（Server Component / `generateMetadata`）で実装しなければ OGP は機能しない。  
> エンジニアへの事前共有が必須。

> **⚠️ High Risk — URLパラメータの未サニタイズによるXSS**  
> keyword パラメータをそのままDOMに埋め込む場合、`<script>` タグ等を仕込まれる可能性がある。  
> Next.js の JSX では基本的にエスケープされるが、`dangerouslySetInnerHTML` や OGP `content` 属性への直接埋め込みを使用する場合は要注意。

## Feature 2: キーワード制限告知バナー

### 概要
Free ユーザーのキーワード件数に応じてバナーを表示する。  
- 7件以上: 警告バナー（あと3件で上限）  
- 10件以上: ブロックバナー（登録不可）  
- ×ボタンで閉じた場合 localStorage に保存  
- Pro ユーザーには表示しない

### リスク先行分析

> **⚠️ High Risk — dismiss後に10件到達した場合のブロックバナー抑制**  
> 警告バナー（7件）を dismiss した localStorage フラグが残ったまま10件に達した場合、  
> ブロックバナーまで非表示になるリスクがある。  
> 警告 dismiss と ブロック表示は別の条件・別の localStorage key で管理すべき。

> **⚠️ Medium Risk — localStorage key 衝突**  
> アプリ固有のkey（例: `kw_limit_dismissed_{appId}`）を使わない場合、  
> アプリAでのdismissがアプリBのバナーを消す可能性がある。

> **⚠️ Medium Risk — リアルタイム件数との同期**  
> バナー表示はAPIレスポンスの件数か？ローカルカウントか？  
> キーワード削除後も7件バナーが残る場合、UXを損ねる。

## Feature 3: AIキャプション一括生成

### 概要
Pro ユーザー限定の「全言語まとめて生成」ボタンを追加。  
6言語（ja / en / zh-Hans / ko / fr / de）分のキャプションを並行生成。  
一部言語の失敗時は成功分のみ適用し、失敗言語をユーザーに通知。

### 既存バックエンド確認済み事項
- `POST /api/apps/{appID}/captions/generate` に `bulk: true` または `language: "all"` で Pro gate 済み
- Free ユーザーの場合 HTTP 403 `"bulk AI caption generation requires Pro plan"` を返す
- `language` が `"all"` の場合の `service.Generate` 内の挙動は未確認（要エンジニア確認）

### リスク先行分析

> **⚠️ Critical Risk — `language="all"` 時の service.Generate の戻り値構造未定義**  
> バックエンド `caption.go` は `language="all"` でも `map[string][]string{"captions": ...}` を返す。  
> 「all」の場合にサービス層が各言語のキャプションをどう返すか（フラット配列？言語→候補のmap？）が未定義。  
> フロントとの I/F を事前にエンジニアと合意する必要がある。  
> **推奨実装**: `{ "captions": { "ja": [...], "en": [...], ... } }` の言語別マップ形式

> **⚠️ High Risk — `Promise.allSettled` vs `Promise.all` の選択**  
> フロントが6件の並列リクエストを `Promise.all` で実行した場合、1件でも失敗すると全体が失敗扱いになる。  
> `Promise.allSettled` を使い、成功した言語のみ適用する実装が必要。

> **⚠️ High Risk — APIレートリミット**  
> Claude API に6リクエストを同時送信するとレートリミット（429）に抵触する可能性がある。  
> バックエンド側でのシリアライズ or バッチ化の検討が必要。

> **⚠️ Medium Risk — 生成中の UI ロック**  
> 6言語生成中（最大30秒程度）にユーザーが言語切替・キャプション手動編集を行うと状態が混乱する。  
> 生成中はフォーム全体を `disabled` にすべき。

> **⚠️ Medium Risk — Free ユーザーが bulk=true を送信した場合のフロント処理**  
> バックエンドは HTTP 403 を返すが、フロントがこれを UpgradeModal に繋ぐ実装が必要。  
> 既存の `aiUsedLangs` による Free gate とは別に、バックエンドの 403 も処理すること。

## エンジニアへの事前共有事項（実装前に確認必須）

1. **LP の SSR 要件**: `generateMetadata()` を使った Server Component にすること。`'use client'` 単独では OGP が機能しない。
2. **`language="all"` のレスポンス形式**: `{ "captions": { "ja": [...], "en": [...] } }` の言語別マップを推奨。フロントとの I/F を事前合意すること。
3. **並列リクエスト方式**: `Promise.allSettled` を使い部分失敗を許容すること。`Promise.all` は使わないこと。
4. **localStorage key の設計**: アプリID別にすること（例: `kw_warning_dismissed_${appId}`）。
5. **ブロックバナーの dismiss フラグは設けないこと**: ブロック状態はユーザーが意図的に無視できてはならない。
